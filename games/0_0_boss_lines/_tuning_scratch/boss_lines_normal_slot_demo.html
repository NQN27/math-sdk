Notes / known simplifications

This engine reimplements the real mechanic from game_config.py/game_bonus.py/game_executables.py: real reel CSVs (byte-for-byte identical to BM_Reels_S1-6.csv, verified), real 15-line matching (contiguous run from reel 0, wild substitution, min kind=3), real per-line paytable CASH payout (L1-L5/H1-H4, separate from and in addition to boss-defeat reward drops - Normal tier's own reels carry zero Wild-Multi/Global-Multi Power symbols, verified against the CSVs, so that scaling layer is correctly inert here and was not ported), real per-instance symbol damage ranges, real wild 2x-highest-substituted damage rule, real boss HP/Dam table with ±25% variance and the 35%-spread reroll, real column→boss routing with live fallback re-evaluation, real mid-spin multi-stage-clear (a hot pass can chain through several boss trios in one spin), real +50/+50 Player HP grant on every stage clear, real Elixir (10-100% of current HP, rounded to nearest 10) and Booster (x2 damage next spin) triggers, real sequential-strip tumble refill with stage-removed-symbol resampling, and the real counter-attack (including the "grace" spin - a freshly-rolled boss trio does not counter-attack after its own first static state).

Honesty check (ran this demo's own headless batch before handing it over, not just asserting it matches) — 2026-08-22, updated after finding and fixing two real missing mechanics:

This demo previously omitted two mechanics that ARE real in game_calculations.py/game_bonus.py: (1) every winning payline pays its own paytable amount as cash, separate from and in addition to boss-defeat reward drops — this demo only ever paid the reward-drop side; (2) the counter-attack "grace" spin on a freshly-rolled boss trio — this demo dealt full counter-attack damage every spin unconditionally, with no grace at all. Both are now implemented and covered by test_demo_sim.js. Fixing them moved this demo's own headless batch a lot: meanCash 45.4x → 63.3x (line-pay alone) → 110.3x (+ grace), stage-6 reach 0.45% → 0.45% → 3.1%, against the Python-confirmed target of mean≈84x / stage6≈1.86% (reshape_segments_test.py, n=100000, segments_n100000_20260822_003530.json).

Both fixes are unambiguously correct (verified against the exact production source, not guessed), and both moved the numbers in the right direction from where they started — but the combined result OVERSHOOTS the Python target rather than landing on it. Every individually- checkable piece was directly diffed against production and matches exactly: all 30 reel strips (byte-for-byte against BM_Reels_S1-6.csv), boss Dam/HP base values and the ±25%-variance/35%- spread reroll, the counter-attack grace grant/consume lifetime (instrumented over 10k sessions: grants≈consumptions, no leak), Elixir heal range, Booster multiplier, the +50/+50 stage-clear HP grant, the chain-block trigger formula, the tumble refill order, boss/column routing distribution, and the removed-symbol resample exclusion set.

2026-08-22, follow-up: an earlier version of this note reported stage-clear survival running "10-26% relatively higher in JS at stages 2-4, root cause open." Chasing that down further found the dominant cause was a bug in the isolated Python test harnesses used to measure it (not in this demo): those harnesses called run_one_bonus_spin directly, bypassing run_bonus_session's per-spin step that turns a collected Booster into booster_multiplier_current_spin for the following spin — so every isolated Python comparison this session was silently missing the real x2-damage-next-spin mechanic (which fires on ~40%+ of spins), while this demo's own JS handles it correctly and internally. Re-measured with that harness bug fixed, mean per-instance boss damage in a matched stage-2 setup came out within ~2% between engines (Python 22.54, JS 22.58-22.75). A real residual survives this correction, confirmed at 8-17 SE across several sample sizes (not sampling noise): mean spins-to-clear stage 2 with fixed boss Dam/HP is Python 6.46, JS 5.99 (~8% higher in Python, n=15000 each), and overall clear-probability under a fixed, finite player-HP budget (250, real boss-variance, stage 2 direct-start) is meaningfully higher in JS (92.7%, n=20000) than Python (65.9%, n=20000).

A follow-up session (2026-08-22) tried to isolate this to a specific mechanism and ruled out every hypothesis it could directly measure: chain-block pass-count interaction (disabling chain-block in both engines leaves the same ~8% gap), same-spin cross-boss damage correlation (matches to 0.1pp), each boss's own per-spin marginal damage distribution (mean/stdev/percentiles/ deciles match to within ~1%, confirmed via bootstrap resampling from each engine's own empirical samples, which predicts an *identical* first-passage time from either engine's marginal alone), spin-to-spin autocorrelation lag 1-5 (small and similar in both, if anything pointing the wrong direction), zero-damage run-length clustering (matches), damage wasted on an already-dead boss (matches, JS wastes slightly *more* — wrong direction), the real "first spin of a stage deals ~30% less damage than steady-state" effect (confirmed real, but present equally in both engines), and a test-harness state-read-after-mutation bug of the same class caught earlier this session (checked directly: the harnesses' two independent ways of detecting a stage clear agree with each other on every single session in both engines, 0/5000 mismatches each). None of these explain the gap. Full test-by-test record: _tuning_scratch/STAGE2_CLEARTIME_INVESTIGATION_FINDINGS.md. Conclusion: the isolated single-stage residual is real, reproducible, and currently unexplained by any distributional mechanism this investigation could isolate — likely a higher-order sequential- dependency effect in the pass/cascade structure, not a single traceable line of code. It affects only this scratch demo-vs-Python-harness comparison, not the production game files.

2026-08-22, second follow-up (fixed): a separate, real, and larger gap was found and fixed during the same session: this demo had zero implementation of production's Bonus "grace spin" (game_executables.create_board_reelstrips's grace_deadspin_pending branch) — a 65% per-column chance to force columns 1/2/3 into a non-connecting dead-spin position on the very first spin against a freshly-rolled trio (the spin right after any non-final stage clear). Measured effect in Python: that spin's mean damage to boss1 drops from the normal ~103 to ~44 (P(zero damage) rises from 27% to 65%) when the grace flag is active — a real, large, Python-only advantage this demo was missing across every stage transition (1→2, 2→3, ... 5→6) in any full multi-stage session, independent of the still-open single-stage residual above. Ported into runOneBonusSpin/clearStage via ctx.graceDeadspinPending + BONUS_GRACE_DEADSPIN_CHANCE=0.65, reusing the existing routeColumnForceDeadspin primitive (same one chain-block uses); verified to reproduce the Python numbers almost exactly (JS: ~104 → ~45, P(zero)=65%) and covered by 3 new checks in test_demo_sim.js section 6 (18/18 passing).

Net effect: treat this demo as correct for FEEL and for every individual mechanic listed above (all independently verified against source), but its own current aggregate mean/stage6% numbers run high relative to the tuned economy - use the Python numbers for the actual payout shape.

Remaining known simplification (both configs): this demo has no wincap/headroom-clamp concept, so an extreme stage-6-chest jackpot tier (including the natural Max Win entry) is paid in full rather than clamped to remaining headroom the way award_win() would in production — a rare, cosmetic-only difference for play-testing purposes. Full validated aggregate numbers (mean≈84x, median≈38x, p75≈84x, stage6≈1.86%, bucket% monotonic s1→s6) live in reshape_segments_test.py's results/ output — use the headless batch panel below to compare this demo's own numbers against those.
